Why this assignment exists

Storing a website on-chain is not what you would ship. That is the point. Doing it drives you head-first into account allocation limits, realloc, rent, transaction size, and the BPF heap — the constraints you normally engineer around without ever seeing them.

By the end you will have hit every one of them personally, and you will be able to argue from experience about when data belongs on-chain and when a pointer does. That argument is the actual deliverable. The website is just how you earn it.

The four walls you will hit

10,240Max bytes for an account created through a CPI. Anchor's init is a CPI.
10,240Max bytes a program can add to an account per instruction.
1,232Max bytes in a transaction — signatures, keys, and all.
32 KBThe BPF heap. Deserialize a big payload into it and you die.

Every awkward design decision in the starter program traces back to one of these four numbers. When something feels convoluted, ask which wall it is dodging.

The account layout

Bytes 0–128 are a fixed header. Everything after byte 128 is the website itself. Do not move these fields — the gateway and the grader read them at fixed offsets.

BytesFieldWhy it exists
0–8discriminatorAnchor's account type tag
8–40authorityWho may write and close
40–72namePDA seed, so one wallet can host many sites
72–104content_hashsha256, committed before upload
104–108total_lenTarget payload size
108–112written_lenHigh-water mark of bytes written
112encoding0 raw, 1 gzip
114finalizedSealed flag
128+payloadYour page

TODO 1 · grow

Grow the account

What this does. initialize created your PDA with exactly 128 bytes — just the header, no room for a page. This instruction stretches it toward its full size, one call at a time.

Why it is not one call. A program may only extend an account by MAX_PERMITTED_DATA_INCREASE — 10,240 bytes — per instruction. A 30 KB page therefore needs three separate transactions before a single byte of content can land. Your job is to make one step of that walk correct and repeatable.

The part everyone forgets. Rent exemption is calculated from the account's size. Make the account bigger without adding lamports and it quietly stops being rent exempt. You must top it up from payer before you resize.

Requirements

  1. Target size is HEADER_LEN + site.total_len.
  2. If the account is already that big, fail with AlreadyFullSize.
  3. New size is min(target, current + MAX_PERMITTED_DATA_INCREASE).
  4. Transfer any rent shortfall from payer to the site account.
  5. Resize.
Hint The borrow checker will fight you

Read total_len off the deserialized account first, then take the AccountInfo. If you hold a mutable borrow of ctx.accounts.site and then call .to_account_info() on it, Rust will refuse — and the error will point somewhere unhelpful. 

let target = HEADER_LEN + ctx.accounts.site.total_len as usize;
let info = ctx.accounts.site.to_account_info();
let current = info.data_len();
Hint Working out the rent shortfall

Rent::get()?.minimum_balance(new_len) tells you what the account needs to hold at the new size. Compare it against info.lamports() and move the difference with system_instruction::transfer through invoke. Only transfer if there is actually a shortfall — an unconditional transfer of zero is a wasted CPI.

Hint Which method actually resizes

info.resize(new_len)?. You may see realloc(new_len, zero_init) in older tutorials; it still works but is deprecated in current versions.

Check yourself Three tests turn green: the account reaches its target size, it stays rent exempt after growing, and a fourth grow call on a full account is rejected.

Write the chunks

What this does. Copies one slice of your file into the account at a byte offset. Called once per slice until the whole page is in place.

Why chunks. A Solana transaction is capped at 1,232 bytes total. After a signature (65), the message header (3), the account keys (~129), a blockhash (32) and the instruction envelope, you have a little under 1,000 bytes of room. The client uses 880-byte slices to keep margin. A 6 KB page is 8 transactions; a 24 KB page is 28.

Order does not matter. The uploader fires six chunks at a time and retries failures, so chunk 7 may land before chunk 3. Write to the offset you are given and track a high-water mark — never assume you are appending.

The 32 KB trap Do not add the payload to the Site struct as a Vec<u8>. Borsh would deserialize the entire page into the BPF heap, which is only 32 KB, and your program would work perfectly on test fixtures and die on a real page. Write to the raw account bytes instead and memory use stays flat at any size.

Requirements

  1. Reject if the site is finalized — AlreadyFinalized.
  2. Reject an empty chunk — EmptyChunk.
  3. Compute end = offset + data.len() with checked arithmetic.
  4. Reject if end > total_len — OutOfBounds.
  5. Reject if HEADER_LEN + end is past the current account size — NotGrownYet.
  6. Copy the bytes in at HEADER_LEN + offset.
  7. Raise written_len to end if end is larger.
Hint Writing to raw account bytes 
let info = ctx.accounts.site.to_account_info();
{
    let mut raw = info.try_borrow_mut_data()?;
    raw[HEADER_LEN + start..HEADER_LEN + end].copy_from_slice(&data);
}

Keep the borrow inside its own block. Anchor writes the header back when the instruction exits, and a borrow still held at that moment will panic at runtime rather than fail to compile.

Hint The off-by-128 that costs an hour

Every offset the client sends is relative to the payload, not the account. Writing at offset instead of HEADER_LEN + offset looks completely successful — every transaction confirms — and then the hash check fails and the page renders as garbage. If checkpoint 4 fails and you cannot see why, this is the first thing to check.

Check yourself Bounds and empty-chunk rejections pass, written_len equals total_len after a full upload, and the round-trip test decompresses the account back to a byte-identical copy of the source file.

TODO 3 · finalize

Seal it

What this does. Flips the account from "under construction" to "done", permanently. After this, write_chunk must fail.

Why bother. Without a seal, your site is a mutable blob that its author can rewrite at any moment — which means a reader can never be sure the bytes they verified are the bytes that will be there tomorrow. Sealing converts the account from storage into an artifact. That single boolean is most of what makes the on-chain version interesting compared to a hosted file.

Requirements

  1. Reject if already finalized.
  2. Reject unless written_len == total_len — IncompleteUpload.
  3. Set finalized = true.
Hint Why the completeness check matters

written_len is a high-water mark, not a count. If chunk 5 of 8 gets dropped, the mark still climbs when chunks 6, 7, and 8 land, and you end up with a hole in the middle of the file. Requiring written_len == total_len only catches a short upload, not a gap — which is exactly why the hash check in checkpoint 4 exists. Sealing is necessary; it is not sufficient.

TODO 4 · verify

Prove it on-chain

What this does. Recomputes sha256 over the bytes actually stored in the account and compares it to the hash initialize committed before the upload began.

Why the ordering is the whole trick. The hash goes on-chain first, when the account is still empty. That means the uploader cannot decide after the fact what the "correct" content was. A passing verify is proof that the chain holds exactly the file that was promised — not merely that it holds a file whose hash matches itself.

This is the same commit-then-prove shape you will see everywhere in the ecosystem. Commit to a value cheaply, reveal later, let anyone check.

Requirements

  1. Slice the payload out of the raw data: HEADER_LEN..HEADER_LEN + total_len.
  2. Hash it and compare against site.content_hash.
  3. Fail with HashMismatch if they differ.
Expect an out-of-compute error first Hashing tens of kilobytes costs far more than the 200,000 CU default. The provided client already sends a ComputeBudgetProgram.setComputeUnitLimit instruction alongside this one. If you write your own client, you need one too — and if you see "exceeded CUs", that is what it means, not a bug in your logic.
Hint Getting the payload slice 
let info = site.to_account_info();
let raw = info.try_borrow_data()?;
let payload = &raw[HEADER_LEN..HEADER_LEN + site.total_len as usize];
let computed = hash(payload).to_bytes();

Immutable borrow this time — you are only reading.

Check yourself Two tests. One uploads honest content and expects verify to pass. The other commits the hash of one page, uploads a different page of identical length, and expects HashMismatch. If the second passes when it should fail, you are hashing the wrong bytes.

TODO 5 · close_site

Reclaim the rent

What this does. Deletes the account and returns every lamport of rent to the authority.

Why it is nearly empty. This is the shortest instruction in the program, and the lesson is where the work happens. Anchor does it declaratively — find the constraint in the CloseSite accounts struct and the body is one line. Constraints are not decoration; they are where a surprising amount of an Anchor program's behavior lives.

Worth sitting with Rent is a refundable deposit, not a fee. You will get your ~0.045 SOL back. That also means an on-chain site is permanent only as long as nobody closes it — which is a real caveat on the word "permanent", and question 3 of the writeup asks you about it.

Build your page

Open site/index.html and replace it with something that is actually yours. Three rules, all graded, all of them there for a reason.

RuleWhy
One file, everything inlinedA second request is a second thing that can disappear
Zero external requests — no CDNs, no web fonts, no remote imagesA page that phones home is not on-chain in any meaningful sense
Under 12 KB gzippedYou are paying rent per byte, forever, out of your own wallet
 
npm run size

# site/index.html
#   raw     2,880 bytes
#   gzipped 1,444 bytes  (12% of budget)
#   rent    0.011832 SOL
#   chunks  2 write transactions
#   PASS ready to upload

The checker rejects any src, stylesheet <link>, CSS url() or @import pointing at another host. Ordinary <a href> links to other sites are fine — a link is not a dependency.

Notice what compression buys you Gzip typically takes a hand-written page down by 70–75%. That is not just cheaper rent — it is proportionally fewer write_chunk transactions, because both costs scale with the same number. One decision, two wins. Writeup question 2 asks you to put real numbers on this.

Deploy

Ship to devnet

anchor deploy --provider.cluster devnet
npx ts-node app/deploy.ts ./site/index.html portfolio --rpc=<your-endpoint>
The site name must be exactly "portfolio" The grader derives your PDA from ["site", your_wallet, "portfolio"]. A different name means a different address and a submission that looks, to an automated check, like you never deployed at all.

The script prints your site address. Now read it back through the gateway — and serve the gateway rather than double-clicking the file, because a file:// origin breaks the RPC call. 

python3 -m http.server 8000
# http://localhost:8000/app/viewer.html?account=<YOUR_PDA>&cluster=devnet

The header strip shows what the gateway found: bytes stored, encoding, rent, sealed state, and a sha256 check it performs itself, in your browser, against the hash on-chain. When that reads verified, the loop is closed — your page went out as chunks, came back from a validator, and proved it was unchanged.

Hint It renders blank

Read the header strip before touching any code.

  • sealed false — finalize never ran.
  • sha256 MISMATCH — your bytes are not what you uploaded. Re-read the off-by-128 hint in checkpoint 2.
  • Nothing at all — wrong cluster, or wrong address.

The pointer

Now build the same thing the way production actually does it: put the bytes on IPFS and keep only the address of those bytes on-chain.

This is not the lesser half

It is the dominant pattern on Solana. Every Metaplex NFT works this way — the on-chain metadata account holds a uri and the image lives on IPFS or Arweave. Token-2022's TokenMetadata extension has a uri field for exactly this, and MetadataPointer exists to declare which account holds the metadata at all. You are hand-building something you will meet again as a standard extension.

What the on-chain record actually buys you

  • Authority. The chain says which CID is current. Without it you need an off-chain directory, which puts back exactly the trust you were removing.
  • Programmability. A program cannot fetch IPFS, but it can store, gate, and transfer a pointer. Ownership of the pointer becomes ownership of the site.
  • Tamper evidence. A CID is a hash. Bytes either match it or they do not.
  • Cheap mutability. A few hundred bytes of rent, and you can republish forever.

Requirements

  1. Pin the same site/index.html to IPFS with Pinata's free tier. You get a CID.
  2. Reject an empty CID — EmptyCid — and one longer than MAX_CID_LEN — CidTooLong.
  3. Store the CID, the authority, and the bump.
  4. Stamp updated_slot from Clock::get()?.slot.
npx ts-node app/pointer.ts set <YOUR_CID> --rpc=<your-endpoint>
npx ts-node app/pointer.ts get
Hint Why this one is mutable on purpose

The accounts struct uses init_if_needed, so a single instruction both creates and updates. Call it again with a new CID and the old one is simply replaced — the opposite of the site account, which you sealed shut in checkpoint 3.

That contrast is the point of running both halves. Writeup question 5 asks what a reinitialization attack is and why this particular use is safe; the answer is in what the instruction writes and what an attacker could gain by re-running it.

Hint You do not need a name for any of this

A CID is already a complete address — https://<CID>.ipfs.dweb.link/ works the moment Pinata gives it to you. ENS and SNS names are a convenience layer that stores a CID; they do not produce one, and nothing here requires registering a domain.

Prefer subdomain gateways over path gateways for HTML. A path gateway puts every site on one shared origin, so all IPFS content there shares localStorage and cookies.

Submit

Writeup & submit

Add WRITEUP.md to your repo. A paragraph each — this is graded on thinking, not length.

  1. Cost. Report the real rent for your site account and your pointer account, in SOL and in bytes. Rent is (128 + data_size) × 3480 × 2 lamports. What is the ratio between them? What would a 1 MB page cost?
  2. Compression. Your page before and after gzip, and the write_chunk count for each. Why does one decision reduce two different costs?
  3. Mutability. The site seals; the pointer never does. What does each property buy, and when would you want the other?
  4. The bootstrap problem. Your site is on-chain, but a browser cannot read a Solana account — something must deliver the gateway over HTTP first. Does that make this pointless? Take a position. What do you still gain, and what have you not gained?
  5. init_if_needed. What is a reinitialization attack, and why is this use safe?
Question 4 is the one that counts It has no clean answer, which is why it is there. A strong response notices that the gateway is generic, replaceable, and cannot lie — the hash was committed on-chain before upload, and any reader re-checks it. A weak response either claims full decentralization or concludes the whole exercise was theatre. Both miss what actually changed hands.

Solution TODO 1 — grow 
pub fn grow(ctx: Context<Grow>) -> Result<()> {
    let target = HEADER_LEN + ctx.accounts.site.total_len as usize;
    let info = ctx.accounts.site.to_account_info();
    let current = info.data_len();
    require!(current < target, SiteError::AlreadyFullSize);

    let new_len = std::cmp::min(target, current + MAX_PERMITTED_DATA_INCREASE);

    let rent = Rent::get()?;
    let required = rent.minimum_balance(new_len);
    let held = info.lamports();
    if required > held {
        invoke(
            &system_instruction::transfer(ctx.accounts.payer.key, info.key, required - held),
            &[
                ctx.accounts.payer.to_account_info(),
                info.clone(),
                ctx.accounts.system_program.to_account_info(),
            ],
        )?;
    }

    info.resize(new_len)?;
    Ok(())
}
Solution TODO 2 — write_chunk 
pub fn write_chunk(ctx: Context<WriteChunk>, offset: u32, data: Vec<u8>) -> Result<()> {
    require!(!ctx.accounts.site.finalized, SiteError::AlreadyFinalized);
    require!(!data.is_empty(), SiteError::EmptyChunk);

    let start = offset as usize;
    let end = start.checked_add(data.len()).ok_or(SiteError::OutOfBounds)?;
    require!(end <= ctx.accounts.site.total_len as usize, SiteError::OutOfBounds);

    let info = ctx.accounts.site.to_account_info();
    require!(HEADER_LEN + end <= info.data_len(), SiteError::NotGrownYet);

    {
        let mut raw = info.try_borrow_mut_data()?;
        raw[HEADER_LEN + start..HEADER_LEN + end].copy_from_slice(&data);
    }

    let site = &mut ctx.accounts.site;
    if end as u32 > site.written_len {
        site.written_len = end as u32;
    }
    Ok(())
}
Solution TODO 3 — finalize 
pub fn finalize(ctx: Context<Finalize>) -> Result<()> {
    let site = &mut ctx.accounts.site;
    require!(!site.finalized, SiteError::AlreadyFinalized);
    require!(site.written_len == site.total_len, SiteError::IncompleteUpload);
    site.finalized = true;
    Ok(())
}
Solution TODO 4 — verify 
pub fn verify(ctx: Context<Verify>) -> Result<()> {
    let site = &ctx.accounts.site;
    let info = site.to_account_info();
    let raw = info.try_borrow_data()?;
    let payload = &raw[HEADER_LEN..HEADER_LEN + site.total_len as usize];
    let computed = hash(payload).to_bytes();
    require!(computed == site.content_hash, SiteError::HashMismatch);
    Ok(())
}

pub fn set_pointer(ctx: Context<SetPointer>, cid: String) -> Result<()> {
    require!(!cid.is_empty(), SiteError::EmptyCid);
    require!(cid.len() <= MAX_CID_LEN, SiteError::CidTooLong);

    let pointer = &mut ctx.accounts.pointer;
    pointer.authority = ctx.accounts.authority.key();
    pointer.cid = cid;
    pointer.updated_slot = Clock::get()?.slot;
    pointer.bump = ctx.bumps.pointer;
    Ok(())

When it breaks

Troubleshooting

Ranked by how often it actually happens.

Error 'site' does not exist in type 'ResolvedAccounts<…>'

Anchor 0.30+ changed .accounts() to accept only accounts it cannot resolve itself. Your site PDA has declared seeds and systemProgram is a known address, so both get stripped from the accepted type. Use .accountsPartial() — same behavior, no filter. The provided scripts already do.

Error 429 Too Many Requests

The public devnet endpoint, shared by everyone. Pass --rpc=<url> with your own free endpoint. This is why checkpoint 0 tells you to get one before writing code.

If it hits during verify after the upload succeeded, your site is fine — verify is confirmation, not deployment. Re-run the command.

Error feature `edition2024` is required

Your Rust is older than the dependency tree. rustup update stable first. If you cannot update, run ./scripts/pin-for-old-toolchain.sh, which pins the six crates that moved to edition 2024.

Worth understanding rather than just running: the crate the error names is usually not the crate that chose the version. Walk up with cargo tree -i <crate> to find who did.

Error No such file or directory (os error 2)

Anchor failed to spawn a binary and will not tell you which one. Run: 

which rustc cargo solana cargo-build-sbf avm agave-install

Whichever comes back empty is your answer. Install Rust through rustup, not Homebrew — a brew Rust lands somewhere Anchor does not look.

Error Everything confirms but the hash is wrong

Almost always write_chunk writing at offset instead of HEADER_LEN + offset. Every transaction succeeds, the account fills up, and the first 128 bytes of your page have overwritten the header while the tail runs off the end.
